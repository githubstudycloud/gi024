# Spring Boot 4 MCP 迁移平台详细设计

## 1. 文档目标

本文档基于 `springboot4-mcp-migration-design.docx` 的迁移思路，结合当前代码仓库的工程约束，输出一版可直接落地编码、可直接映射到仓库结构的详细设计。

本次设计相对于原始设想做了三项明确收敛：

- 构建工具固定为 Maven，多模块组织，不再额外引入 Gradle 或单独的 BOM 模块。
- 新系统运行时固定采用 PostgreSQL，数据库变更统一通过 Flyway 管理；测试环境使用 H2 PostgreSQL 兼容模式复用脚本。
- 业务域从“用户域 + 订单域”扩展为“用户域 + 订单域 + 商品域”，用第三个领域验证迁移模式可复制。

## 2. 设计原则

### 2.1 总体原则

- 保留旧系统为迁移初期的权威数据源。
- 新系统通过 ACL 访问旧系统，避免上层直接依赖旧系统协议。
- REST 与 MCP 共享同一套应用服务，避免双份业务逻辑。
- 通过特性开关按业务域控制流量走向，而不是一次性全量切换。
- 新系统数据库结构必须可追溯、可回放，因此统一采用 Flyway 管理。

### 2.2 本次工程化取舍

- 使用 Spring Boot `4.0.5`。
- 使用 Spring AI `2.0.0-M4` 与注解式 MCP Server。
- 保留六边形架构思想，但不做过度拆分。
- 开发态允许自动灌入样板数据，生产默认不做任何初始化写入。

## 3. 工程结构

### 3.1 目录结构

```text
springboot4-mcp-platform/
├── docs/
│   └── 详细设计.md
├── mcp-domain/
├── mcp-application/
├── mcp-acl/
├── mcp-infrastructure-jpa/
├── mcp-rest-api/
├── mcp-mcp-server/
├── mcp-bootstrap/
├── pom.xml
└── README.md
```

### 3.2 模块职责

- `mcp-domain`
  只放领域模型、分页结构、端口接口和领域异常，不依赖 Spring 与外部技术栈。
- `mcp-application`
  放应用服务、输入校验和迁移开关路由逻辑。
- `mcp-acl`
  放旧系统 REST 客户端、旧 DTO、映射器和旧系统异常归一化逻辑。
- `mcp-infrastructure-jpa`
  放新系统实体、Repository 与基于 JPA 的查询适配器。
- `mcp-rest-api`
  放对外 REST 控制器、响应 DTO 和统一异常处理。
- `mcp-mcp-server`
  放 MCP Tool、Resource、Prompt 提供者。
- `mcp-bootstrap`
  放应用启动类、配置、Flyway 脚本、开发初始化和冒烟测试。

## 4. 迁移运行模型

### 4.1 数据源切换方式

每个业务域独立维护一个迁移开关：

```yaml
migration:
  flags:
    user-source-new: false
    order-source-new: false
    product-source-new: false
```

应用服务读取对应开关后，决定调用：

- `Legacy*Gateway`，访问旧系统。
- `New*QueryGateway`，访问新系统 JPA。

这样可以支持三种典型迁移节奏：

- 某个域先完全走旧系统。
- 某个域切到新系统，其他域继续走旧系统。
- 全部域切到新系统做联调或回归测试。

### 4.2 请求流转

以商品域为例，请求流转如下：

1. REST 或 MCP 入口接收请求。
2. 调用 `ProductQueryUseCase`。
3. `ProductQueryService` 根据 `product-source-new` 选择旧系统或新系统查询网关。
4. 旧系统路径经 ACL 做协议转换；新系统路径经 JPA 查询并映射为统一领域模型。
5. 最终返回统一领域对象，再由 REST DTO 或 MCP View 做出口转换。

## 5. 领域设计

### 5.1 用户域

用户域的统一模型为 `UserProfile`，字段包括：

- `id`
- `username`
- `displayName`
- `email`
- `role`
- `active`
- `createdAt`

用户域是最小迁移样板，旧系统协议仍保持简单形式：

- `GET /api/users`
- `GET /api/users/{id}`
- `GET /api/users/active-count`

### 5.2 订单域

订单域的统一模型为 `OrderRecord`，字段包括：

- `id`
- `orderNo`
- `customerName`
- `status`
- `amount`
- `currency`
- `createdAt`

订单域已经切换为更贴近真实存量系统的协议约束：

- 外层统一响应信封：`code/message/data`
- 列表查询使用 1 基分页：`pageNo/pageSize/totalCount`
- 接口路径通过配置驱动，而不是硬编码在客户端中

默认旧系统路径：

- `/legacy-api/orders/page`
- `/legacy-api/orders/{id}`
- `/legacy-api/orders/statistics/pending`

### 5.3 商品域

商品域的统一模型为 `ProductRecord`，字段包括：

- `id`
- `productCode`
- `name`
- `category`
- `price`
- `currency`
- `active`
- `createdAt`

商品域完整复用订单域迁移模式，旧系统协议也使用统一响应信封和 1 基分页：

- `/legacy-api/products/page`
- `/legacy-api/products/{id}`
- `/legacy-api/products/statistics/active`

商品域的加入用于证明迁移模式已从“单一案例”变为“可复制模板”。

## 6. 旧系统 ACL 设计

### 6.1 统一职责

ACL 层负责四类事情：

- 使用 `RestClient` 调用旧系统。
- 接收旧 DTO，并映射为新领域模型。
- 将旧系统异常统一翻译为 `LegacySystemException`。
- 记录可观测埋点，便于后续接入 Micrometer / OpenTelemetry。

### 6.2 订单与商品的旧协议约束

订单域和商品域的列表接口统一采用：

```json
{
  "code": "0000",
  "message": "success",
  "data": {
    "records": [],
    "pageNo": 1,
    "pageSize": 20,
    "totalCount": 0
  }
}
```

其中：

- `code` 由 `legacy.success-code` 配置控制，默认 `0000`。
- 当业务码不等于成功码时，ACL 直接抛出 `LegacySystemException`。
- 旧系统时间字段统一由 Mapper 转成 UTC `Instant`。

### 6.3 可配置项

当前仓库中与旧系统访问相关的配置如下：

```yaml
legacy:
  base-url: http://localhost:8088
  connect-timeout: 3s
  read-timeout: 10s
  success-code: "0000"
  order:
    search-path: /legacy-api/orders/page
    detail-path: /legacy-api/orders/{id}
    pending-count-path: /legacy-api/orders/statistics/pending
  product:
    search-path: /legacy-api/products/page
    detail-path: /legacy-api/products/{id}
    active-count-path: /legacy-api/products/statistics/active
```

## 7. 新系统数据源设计

### 7.1 数据库选型

新系统运行时使用 PostgreSQL。原因如下：

- 更符合真实生产环境。
- 便于 Flyway 做结构演进。
- 能验证从样板阶段过渡到正式项目所需的数据库治理方式。

测试环境使用 H2 的 PostgreSQL 兼容模式，保证：

- 测试不依赖外部数据库。
- 迁移脚本仍然能被校验。

### 7.2 Flyway 脚本规划

当前共三版建表脚本：

- `V1__create_users.sql`
- `V2__create_orders.sql`
- `V3__create_products.sql`

表结构分别对应：

- `users`
- `orders`
- `products`

应用统一设置：

- `spring.jpa.hibernate.ddl-auto=validate`

这样可以强制要求数据库结构先通过 Flyway 迁移，再由 JPA 做启动时校验。

### 7.3 开发样板数据

`DemoDataInitializer` 仅在 `dev` profile 下启用，并采用按表幂等补数的方式：

- 如果 `users` 为空，则初始化用户样板数据。
- 如果 `orders` 为空，则初始化订单样板数据。
- 如果 `products` 为空，则初始化商品样板数据。

这样可以避免后续新增领域时，因为旧表已有数据导致新表样板数据永远无法补齐。

## 8. REST 设计

### 8.1 REST 路径

当前对外统一暴露 `v2` 路径：

- `GET /api/v2/users`
- `GET /api/v2/users/{id}`
- `GET /api/v2/orders`
- `GET /api/v2/orders/{id}`
- `GET /api/v2/products`
- `GET /api/v2/products/{id}`

### 8.2 返回结构

REST 层不直接暴露领域对象，而是返回专用 DTO。分页响应统一包含：

- `items`
- `page`
- `size`
- `total`
- `servedBy`

`servedBy` 用于标记本次请求命中了 `legacy` 还是 `new`，便于灰度联调和迁移验收。

### 8.3 异常处理

统一使用 `ProblemDetail` 返回错误结果，并对以下异常做专门翻译：

- `UserNotFoundException`
- `OrderNotFoundException`
- `ProductNotFoundException`
- `LegacySystemException`
- `IllegalArgumentException`
- `MethodArgumentNotValidException`

所有文案与注释均使用中文，符合当前项目约束。

## 9. MCP 设计

### 9.1 用户域 MCP

- Tool：`search_users`、`get_user_detail`
- Resource：`mcp://users/active-count`
- Prompt：`weekly_user_summary`

### 9.2 订单域 MCP

- Tool：`search_orders`、`get_order_detail`
- Resource：`mcp://orders/pending-count`
- Prompt：`weekly_order_summary`

### 9.3 商品域 MCP

- Tool：`search_products`、`get_product_detail`
- Resource：`mcp://products/active-count`
- Prompt：`weekly_product_summary`

### 9.4 设计约束

- MCP 与 REST 复用同一套 `*QueryUseCase`。
- MCP Resource 返回结构化 JSON 片段，便于模型消费。
- MCP Prompt 负责组织业务上下文，不重复实现查询逻辑。

## 10. 测试设计

### 10.1 应用服务层

在 `mcp-application` 中验证：

- 迁移开关是否按业务域生效。
- 新旧网关切换后 `servedBy` 是否正确。
- 参数校验是否按预期抛错。

### 10.2 ACL 层

在 `mcp-acl` 中通过 `MockRestServiceServer` 验证：

- 旧系统列表、详情、统计接口映射是否正确。
- 订单域和商品域的信封响应体是否能正确解包。
- 上游返回错误码或 HTTP 错误时是否能归一为 `LegacySystemException`。

### 10.3 启动层

在 `mcp-bootstrap` 中做上下文冒烟测试，验证：

- Flyway 迁移可执行。
- JPA 实体与 Repository 可以正常装配。
- REST 控制器可以加载。
- MCP Provider 可以被 Spring 扫描并注册。

## 11. 当前交付范围

本轮交付已经覆盖：

- 三个业务域的查询迁移样板。
- 订单域的真实旧协议适配改造。
- 商品域作为第三业务域的完整打通。
- PostgreSQL + Flyway 的新系统运行时方案。
- 中文设计文档、中文注释、中文异常说明。

暂不纳入本轮的内容：

- 真正的 API Gateway 路由工程。
- 数据回流与双写同步任务。
- OAuth2 / JWT 生产级认证。
- 熔断、限流、缓存等生产增强能力。

## 12. 后续演进建议

- 将用户域也升级为与订单域一致的可配置旧协议模型，统一 ACL 风格。
- 增加第四个业务域，例如库存域，用于继续验证模板可复制性。
- 为 Flyway 增加真实索引优化、唯一约束与审计字段。
- 在迁移开关之外补充灰度发布、对账脚本和双轨验收能力。
