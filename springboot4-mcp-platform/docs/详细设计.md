# Spring Boot 4 MCP 迁移平台详细设计

## 1. 文档目标

本文档基于 `springboot4-mcp-migration-design.docx` 的迁移思路，结合当前开发环境与依赖现状，输出一版可直接落地编码的中文详细设计。目标不是把原始设计逐字翻译，而是在保持核心迁移原则不变的前提下，补齐以下内容：

- 明确首期工程边界，先实现“用户域”，再扩展“订单域”作为第二个迁移样板。
- 将原方案中的抽象模块拆分收敛成更易验证的 Maven 多模块工程。
- 明确哪些能力在首期必须实现，哪些只保留扩展点。
- 让代码结构、配置、测试和后续演进路线一一对应，避免“文档能讲通、代码搭不起来”。

## 2. 对原始设计的调整与完善

### 2.1 保留的核心原则

- 保留“双系统并行、接口按域逐步迁移”的总体策略。
- 保留“旧系统是权威数据源，新系统通过 ACL 访问旧系统”的过渡模型。
- 保留“REST API 与 MCP Tool/Resource 共享同一应用服务”的设计。
- 保留“特性开关控制新旧数据源切换”的迁移机制。
- 保留“六边形架构”思想，但首期不过度拆分，避免空模块过多。

### 2.2 结合现状做出的工程化调整

- 构建工具从 Gradle Kotlin DSL 调整为 Maven 多模块。
  - 原因：当前环境已安装 Maven 3.9.11，未安装 Gradle。
  - 影响：不改变架构分层，只改变工程组织和依赖管理方式。
- 首期不单独创建 BOM 模块。
  - 原因：对于当前样板工程，根 `pom.xml` 统一做版本管理更直接。
  - 后续：当域模块数量增多时，再拆出独立 BOM 更合理。
- 首期不实现网关模块。
  - 原因：API Gateway/Nginx 属于部署层能力，不应强行塞进应用仓库。
  - 后续：在部署仓库或 Helm Chart 中维护路由规则。
- 首期 MCP 传输优先使用 Spring AI 当前推荐的 Streamable-HTTP / WebMVC Server Starter。
  - 原因：Spring AI 2.0.x 已用新的 MCP Server Starter 形态，SSE 不再是唯一入口。
  - 说明：如果后续外部客户端只支持 SSE，可在引导模块中追加兼容配置。
- 首期数据库使用 H2 演示“新数据源”路径。
  - 原因：样板工程需要能够本地直接启动和测试。
  - 后续：切换到 PostgreSQL 时只需替换数据源配置和 Flyway 脚本。

## 3. 首期交付范围

### 3.1 必须实现

- Maven 多模块 Spring Boot 4 工程骨架。
- 用户域与订单域的六边形分层样板。
- ACL 调用旧系统用户接口与订单接口的适配器。
- 基于特性开关的用户查询与订单查询路由。
- REST `v2` 用户查询接口与订单查询接口。
- MCP 用户工具、资源、提示词样板，以及订单域 MCP 样板。
- 全局异常处理。
- 示例配置与启动说明。
- 至少覆盖以下测试：
  - 应用服务路由测试。
  - ACL 映射测试。
  - 启动上下文烟雾测试。

### 3.2 暂不实现但保留扩展点

- 真正的 API Gateway 路由配置。
- 旧系统到新系统的数据同步任务。
- OAuth2/JWT 生产级认证接入。
- 多域迁移能力（订单、商品、库存等）。
- 生产级限流、熔断、降级与缓存。
- Flyway/Liquibase 的真实数据库变更脚本。

## 4. 工程结构设计

### 4.1 目录结构

```text
springboot4-mcp-platform/
├── docs/
│   └── 详细设计.md
├── pom.xml
├── README.md
├── mcp-domain/
├── mcp-application/
├── mcp-acl/
├── mcp-infrastructure-jpa/
├── mcp-rest-api/
├── mcp-mcp-server/
└── mcp-bootstrap/
```

### 4.2 模块职责

#### `mcp-domain`

- 只放纯领域对象、分页结果、端口接口和领域异常。
- 不依赖 Spring，不依赖数据库，不依赖 HTTP。
- 这是后续替换适配器时最稳定的部分。

#### `mcp-application`

- 承载用户查询用例与迁移路由逻辑。
- 负责判断数据源来自旧系统还是新系统。
- 依赖 `mcp-domain`，对外暴露 Spring Bean。

#### `mcp-acl`

- 负责调用旧系统 REST API。
- 负责旧 DTO 到新领域模型的转换。
- 负责把旧系统错误转换成统一异常。
- 首期只实现用户查询相关接口。

#### `mcp-infrastructure-jpa`

- 负责“新系统数据源”的 JPA 实现。
- 提供用户实体、仓储和领域端口适配器。
- 首期只提供读能力，用来演示切换到新路径后的行为。

#### `mcp-rest-api`

- 提供 `/api/v2/users` 相关 REST 接口。
- 输入输出 DTO 与全局异常处理放在这里。
- 不直接接触旧系统与数据库实现细节。

#### `mcp-mcp-server`

- 提供 MCP Tool、Resource、Prompt。
- 复用和 REST 相同的应用服务，不重复实现业务逻辑。
- 输出面向 AI 客户端可理解的结构化结果。

#### `mcp-bootstrap`

- Spring Boot 启动模块。
- 聚合所有子模块。
- 放置 `application.yml`、启动类、开发态数据初始化和集成测试。

## 5. 用户域详细设计

### 5.1 领域模型

首期用户域使用 `UserProfile` 作为统一领域对象，字段如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `String` | 用户唯一标识 |
| `username` | `String` | 登录名 |
| `displayName` | `String` | 展示名 |
| `email` | `String` | 邮箱 |
| `role` | `String` | 角色 |
| `active` | `boolean` | 是否启用 |
| `createdAt` | `Instant` | 创建时间 |

设计要点：

- 旧系统字段命名可能是下划线风格，例如 `user_name`、`create_time`。
- 领域模型统一使用新的命名和时间类型。
- 所有进入新系统的用户数据都必须先转换成领域模型，禁止上层直接使用旧 DTO。

### 5.2 应用服务

定义 `UserQueryUseCase` 作为对外统一入口，包含以下能力：

- `search(query, role, page, size)`：分页搜索用户。
- `findById(id)`：查询用户详情。
- `countActiveUsers()`：统计活跃用户数。
- `buildWeeklySummaryPrompt(week)`：为 MCP Prompt 生成业务提示上下文。

`UserQueryService` 的核心逻辑：

1. 读取迁移开关 `migration.flags.user-source-new`。
2. 若为 `false`，调用 `LegacyUserGateway` 走旧系统。
3. 若为 `true`，调用 `NewUserQueryGateway` 走新系统 JPA。
4. 两条路径最终都返回统一领域模型。

### 5.3 旧系统 ACL 设计

#### 旧系统假设接口

为使样板可编码，首期约定旧系统提供以下接口：

- `GET /api/users?q={query}&role={role}&page={page}&size={size}`
- `GET /api/users/{id}`
- `GET /api/users/active-count`

#### ACL 映射策略

- 使用 `RestClient` 调用旧系统。
- 使用独立 Mapper 做字段转换，不把转换逻辑散落在适配器中。
- 旧系统时间格式约定为 `yyyy-MM-dd HH:mm:ss`，统一转成 UTC `Instant`。
- 一旦旧系统返回非 2xx，抛出 `LegacySystemException`。

#### ACL 超时与可靠性

首期实现以下基础能力：

- `connect-timeout`
- `read-timeout`
- 结构化错误信息
- 观测埋点入口

熔断、重试、缓存只在配置项与代码结构中预留，不在首期强上复杂实现，避免样板代码过度工程化。

## 6. 新系统数据源设计

### 6.1 实体设计

使用 `UserEntity` 对应新库中的 `users` 表，字段与领域对象基本一致。

### 6.2 仓储设计

使用 Spring Data JPA 提供：

- `findById`
- `countByActiveTrue`
- 分页搜索（`Specification`）

### 6.3 样板数据策略

为保证本地可直接演示：

- 开发环境默认插入少量演示用户数据。
- 测试环境使用 H2 内存库。
- 生产环境再切换到 PostgreSQL。

## 6.1 订单域详细设计

### 6.1.1 领域模型

订单域使用 `OrderRecord` 作为统一领域对象，字段如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `String` | 订单唯一标识 |
| `orderNo` | `String` | 订单号 |
| `customerName` | `String` | 客户名称 |
| `status` | `String` | 订单状态 |
| `amount` | `BigDecimal` | 订单金额 |
| `currency` | `String` | 币种 |
| `createdAt` | `Instant` | 创建时间 |

### 6.1.2 应用服务

定义 `OrderQueryUseCase` 作为订单域统一入口，包含以下能力：

- `search(query, status, page, size)`：分页搜索订单。
- `findById(id)`：查询订单详情。
- `countPendingOrders()`：统计待处理订单数。
- `buildWeeklySummaryPrompt(week)`：生成订单周报提示词。

`OrderQueryService` 的核心逻辑和用户域保持一致：

1. 读取 `migration.flags.order-source-new`。
2. 若为 `false`，调用 `LegacyOrderGateway` 走旧系统。
3. 若为 `true`，调用 `NewOrderQueryGateway` 走新系统 JPA。

### 6.1.3 旧系统订单接口约定

- `GET /api/orders?q={query}&status={status}&page={page}&size={size}`
- `GET /api/orders/{id}`
- `GET /api/orders/pending-count`

### 6.1.4 REST 接口

- `GET /api/v2/orders`
- `GET /api/v2/orders/{id}`

### 6.1.5 MCP 能力

- Tool:
  - `search_orders`
  - `get_order_detail`
- Resource:
  - `mcp://orders/pending-count`
- Prompt:
  - `weekly_order_summary`

## 7. REST API 设计

### 7.1 接口定义

#### 查询用户列表

- 方法：`GET`
- 路径：`/api/v2/users`
- 参数：
  - `query`：必填，关键词
  - `role`：选填，角色过滤
  - `page`：选填，默认 `0`
  - `size`：选填，默认 `20`

#### 查询用户详情

- 方法：`GET`
- 路径：`/api/v2/users/{id}`

### 7.2 响应设计

REST 层不直接暴露领域对象，返回专用 DTO：

- `UserResponse`
- `PageResponse<T>`

附加改进：

- 在分页响应中返回 `servedBy` 字段，用于标识本次数据来自 `legacy` 还是 `new`。
- 这有助于联调、灰度验证和迁移验收。

## 8. MCP 设计

### 8.1 Tool

首期实现两个 Tool：

- `search_users`
  - 用途：按关键字、角色分页搜索用户
- `get_user_detail`
  - 用途：根据用户 ID 获取详情

### 8.2 Resource

首期实现一个 Resource：

- `mcp://users/active-count`
  - 用途：返回当前活跃用户数量

### 8.3 Prompt

首期实现一个 Prompt：

- `weekly_user_summary`
  - 输入：`week`
  - 输出：指导 AI 客户端如何结合 Tool/Resource 生成周度用户分析摘要

### 8.4 MCP 与 REST 的关系

- MCP 和 REST 共用同一个 `UserQueryUseCase`。
- MCP 负责“给 AI 用”，REST 负责“给前端或第三方系统用”。
- 这保证任何一次迁移切换都只需改应用服务，不需要双份改造。

## 9. 配置设计

### 9.1 关键配置项

```yaml
migration:
  flags:
    user-source-new: false

legacy:
  base-url: http://localhost:8088
  connect-timeout: 3s
  read-timeout: 10s

spring:
  ai:
    mcp:
      server:
        enabled: true
        name: springboot4-mcp-platform
        version: 1.0.0
```

### 9.2 配置约束

- `application.yml` 放默认配置，默认走旧系统，符合迁移初期原则。
- `application-dev.yml` 打开 `user-source-new=true`，便于本地启动演示。
- `application-test.yml` 使用 H2，并按测试需要覆盖配置。

## 10. 异常与可观测性设计

### 10.1 异常分类

- `UserNotFoundException`
- `LegacySystemException`
- `IllegalArgumentException`（输入校验失败）

### 10.2 REST 错误返回

统一使用 Spring Boot 4 的 `ProblemDetail` 返回错误信息，所有文案用中文。

### 10.3 观测点

首期至少保留以下埋点位置：

- 应用服务入口
- ACL 调用旧系统
- 新库查询路径

后续可接 Micrometer、OpenTelemetry、Prometheus。
